# Spring Boot 毕业设计 —— 设计与编码实施助手

## 用途

把「本科毕设」标准化为 **5 个阶段**（设计 4 + 编码 1），用尽量少的对话轮次产出 **互相一致、覆盖边界情况、可支撑答辩**的交付物，并能按阶段表一步步把代码实现出来。
核心目标：**减少来回追问的轮次（省积分）**，同时**不牺牲边界覆盖与设计准确性**。

## 何时使用

- 用户给出一个新题目（"我要做一个 XX 管理系统作为毕设 / 课程设计"）
- 用户要求生成或更新：需求分析、接口清单、数据库设计、原型、缺口分析
- 用户追问"还有什么没考虑到""边界情况有哪些""答辩会问什么"

## 核心原则（必须遵守）

1. **先批量澄清，再动手。** 不要边问边改。一次性抛出《待确认问题清单》，每条给【推荐方案 + 理由 + 备选】，让用户**用一条消息批量拍板**。
2. **边界优先。** 每写一个功能，必须同时回答三类边界：**输入异常** / **并发与一致性** / **外部依赖失败**。只写主流程的设计不合格。
3. **主动指出漏洞。** 用户思路里的物理约束、职责边界、过度设计要直说，并给理由与替代方案。不要为了顺着用户而放过矛盾。
4. **明确"不做什么"。** 每份文档都要有"不做范围"章节，防止范围蔓延 —— 这也是答辩加分项。
5. **一切以可演示为准。** 原型必须**单文件、零依赖**、可直接双击打开；用模拟器替代真实硬件 / 支付渠道。
6. **一致性优先于篇幅。** 表数、接口数、错误码数必须在各文档之间对得上；头部声明与正文必须一致。
7. **多端 = 多会话，C 端不感知 B 端。** 角色 ≥ 2 时：会话**按角色分槽**存、发请求**按接口路径**选 token、
   401 **只清出错那一侧**；用户端页面不得出现任何后台痕迹（登录 tab、切换身份、Swagger/原型链接、调试按钮）。
   这两条不是"优化项"，写错了就是"两个端同时坏"和"产品观感崩"（详见 `references/edge-and-defense.md` A5.1 / A5.2）。

## 工作流程（5 阶段：设计 4 + 编码 1）

### 阶段 0 · 摸底（1 轮）

确认 5 件事，缺什么问什么：

| # | 要确认的 | 示例 |
|---|---|---|
| 1 | **题目与业务域** | 停车场计费 / 图书馆借阅 / 实验室预约 / 社区团购 …… |
| 2 | **角色与端** | 管理端 / 员工端 / 用户端(H5) / 硬件模拟器。<br>⚠️ **必须追问两件事**：① 用户端**是否需要感知**管理端的存在？② 各端**共用**登录入口还是**各自独立**？<br>— 答案为"不感知 / 独立"时，就要做**登录入口物理分离**；角色 ≥2 时还要做**会话分槽**（详见 `references/edge-and-defense.md` A5.1 / A5.2） |
| 3 | **技术栈与约束** | 见上文《本机工具链约定》——JDK 21 + IDEA 内置 Maven 3.8.1 已固定，**不用问、也不许换**；只需确认 MySQL/Redis 是否可用、是否禁 Docker、是否单体 |
| 4 | **演示方式** | 现场演示 / 录屏 / 模拟器替代硬件 |
| 5 | **交付边界** | 只做设计文档 + 原型，还是也要生成代码？ |

### 阶段 1 · 批量澄清（1 轮）⭐ 省 token 的核心

产出《待确认问题清单》，**必须**含【推荐方案】与【理由】，让用户能一条消息回复：

```markdown
| 编号 | 问题 | 推荐方案（默认） | 理由 | 备选 |
|---|---|---|---|---|
| A | 是否做 XX 功能 | 做（最简形态） | 是核心亮点，且不引入额外依赖 | 不做 / 做完整版 |
| B | 唯一性如何保证 | 数据库唯一索引 + 业务兜底 | 并发下 DB 约束更可靠 | 仅业务校验 |
```

规则：

- **只对真正影响架构的分叉**使用交互式选择（同批 ≤ 4 项）。
- 其余项**直接给推荐默认值并推进**，标注"如需修改请指出"。
- 用户回复后**不要再逐条确认**，直接进入阶段 2。

### 阶段 2 · 生成（1 轮产出全部 6 份）

严格按 `references/doc-specs.md` 的章节结构生成，**不要漏章节**：

> 📁 **目录约定**：所有文档与原型统一归档在项目根的 `docs/` 目录下
> （`docs/需求分析.md`、`docs/接口清单.md`、`docs/prototype/index.html` 等），
> 项目根只保留 `README.md` 与代码目录。

1. `docs/需求分析.md` —— 最厚，含业务逻辑 / 边界 / 异常处理 / 验收标准 / 答辩清单
2. `接口清单.md` —— 总览 + 详情 + 枚举字典 + 错误码表 + 幂等约定 + 权限规则
3. `数据库设计.md` —— 设计决策表 + ER 图 + 表清单 + 完整 DDL + 索引说明
4. `prototype/index.html` —— 单文件多角色可交互原型
5. `待确认问题与缺口分析.md` —— 决策落地记录 + 缺口 + 行动清单
6. `版本更迭记录.md` —— 决策台账 + 踩坑记录 + 交付物清单

> 项目根目录放 `README.md` 作为统一入口（文档地图 + 技术栈 + 快速开始 + 环境陷阱）。

### 阶段 3 · 校验（1 轮）

1. 运行 `scripts/verify_consistency.py <项目根目录>` 做一致性检查。
2. 若环境有 MySQL，**实际执行 DDL 建库 + 灌演示数据**，用 `SHOW TABLES` / `COUNT(*)` 验证。
3. 若生成 HTML 原型，做 JS 语法与标签配对检查（`node --check` + 标签配对 + 外部依赖扫描）。
4. 若有浏览器，用 headless Chrome 跑一遍原型全流程回归，**控制台错误必须为 0**。
5. 报告 ✅通过项 / ⚠️需修项，**并直接修复**后复验。

### 阶段 4 · 编码（按《功能阶段表与实施路线图.md》一步步推进）⭐

**铁律：全程 AI coding，但必须一步一验，不许一次性甩出整个工程。**

1. **先出施工图**：把功能点按 `W0~W9` 阶段排布，每条标注
   【依赖 / 被依赖 / 耦合度（🔴🔴极高 / 🔴高 / 🟡中 / 🟢低）/ 复杂度 / 验收标准】，
   并画 Mermaid 依赖拓扑图。
2. **标出三类危险关系**：
   - **耦合枢纽**（被 3+ 个功能依赖）→ 抽独立 Service，入参只用 DTO，避免上游变更穿透；
   - **双向耦合 / 循环依赖** → 用「状态标记 + 前置校验」破环，**绝不能互相调用**（会 `BeanCurrentlyInCreationException`）；
   - **不能返工的点**（表结构、`BigDecimal`、唯一索引幂等、快照…）→ 列成清单，做之前先对照。
3. **一个阶段 = 一次交付**：每阶段拆成 3~5 步，每步「写 → 编译/启动/跑测试 → 一行汇报」，
   不堆积未验证的代码。**每步做完必须能跑起来**。
4. **每阶段结束跑一次回归**：DDL + 数据 + 校验 SQL + 原型回归，确认没打坏已有功能。
5. **实体/Mapper 不要手写**：从已定稿的 DDL 用 Python 脚本读 `information_schema` 反向生成，
   零依赖、且保证与表 100% 一致（**不要用 `mybatis-plus-generator`**，见上文）。
6. **把坑前置**：编码前先过一遍技术实现坑清单（框架依赖 / 数据库 SQL / 导入导出 / 前端接口 / 定时缓存），
   这些比业务逻辑更容易浪费时间。

## 迭代规则（用户提新需求时）

1. 判断属于**新增功能**还是**语义修正**。
2. **语义修正必须检查是否与既有设计矛盾** —— 旧的判定式、旧的字段语义、旧文档的说明。
3. 更新受影响的**全部**文档 + 原型 + 版本记录（不要只改一处）。
4. **语义修正必须升版本号**（v2.0 → v2.1），并在《版本更迭记录》写清「用户原话 / 为什么改 / 改了什么 / 实测证据」。
5. 发现旧文档与自己新结论冲突时，**同步修正旧处**，并在回复中指出。

## 关键检查点（易漏，务必自查）

- [ ] 状态字段的**语义**会被后续功能误用吗？（"业务门槛" vs "事后审计标记"）
- [ ] 计数类字段**幂等**吗？重复触发会不会重复扣减？
- [ ] 「系统能不能**物理阻止** X」—— 不能就必须写明由线下/人工兜底，并划清职责边界。
- [ ] 头部声明的数量（表数/接口数/错误码数）与正文一致吗？
- [ ] 是否残留**已删除的僵尸接口 / 僵尸表 / 僵尸字段**的引用？
- [ ] 错误码有**重复占用**吗？段位是否为未来功能预留？
- [ ] 金额用 `BigDecimal` / `DECIMAL` 而非 `double` 吗？
- [ ] 有历史快照需求吗（改价后历史订单金额不能变）？
- [ ] 原型里是否残留与新设计矛盾的**假数据 / 假文案**？
- [ ] **同一浏览器同时登两个角色，会话会互相覆盖吗？** 401 会不会把另一侧也清掉？（→ `edge-and-defense.md` A5.1）
- [ ] **C 端页面上有 B 端的入口 / 文案 / 调试链接吗？** 用户误敲后台地址，提示是否泄漏了后台的存在？（→ A5.2）
