# 接口文档编写规范（通用）

> **第 11 节是硬约束，与本文其它章节冲突时，以硬约束为准。**

## 1. 适用与产物

| 项 | 内容 |
|---|---|
| 产物 | 项目约定的**一个**接口文档文件（默认 `doc/接口文档.md`），不新建分册 |
| 读者 | 接接口的人：前端、客户端、第三方开发者。他们不做服务端实现，只调方法或发请求 |
| 交付标准 | 对方拿到就能写代码：调哪个方法、传什么、回来什么、什么情况算成功、失败怎么提示 |
| 不写 | 实现原理、协议字节格式、帧结构、数据库表结构、大段调用示例 |

## 2. 取材顺序（禁止臆造）

1. **调用方 SDK / 封装层** —— 方法名、参数顺序、返回字段**以它为准**
2. **服务端实现** —— 路由/handler/service：真实语义、状态码、字段名、上限、空值含义
3. **协议定义** —— 命令号、枚举、错误码的权威出处
4. **实际调一次** —— 启动服务跑一遍，把真实响应写进"注意"

四者冲突时按 **实测 > SDK > 服务端源码 > 旧文档** 取值。旧文档永远最后信，它最可能是过期的。

## 3. 文档骨架（固定层级，不增删）

```
# 一、接口说明
    一句话导语：说明调用方用什么封装、读完能做什么
## 1.概要
### 1.1 通用返回格式     ← 外层包装 + 字段表
### 1.2 code 取值        ← 全部业务码一张表，含 message 与调用方处理建议
### 1.3 请求地址         ← 端点信息（见下表）
## 2.<第一个接口>
## 3.<第二个接口>
...
## N.辅助方法           ← 工具方法/枚举/错误码明细，固定放最后
```

`1.3 请求地址` 按协议填，别漏：

| 协议 | 该写什么 |
|---|---|
| HTTP/REST | base URL、路径前缀、认证方式（Header/Token）、Content-Type |
| WebSocket | 连接地址（`ws://…`）、握手参数、心跳间隔、消息格式 |
| RPC（gRPC 等） | 服务名、endpoint、是否需要 TLS、超时 |
| TCP 自定义协议 | `host:port`、是否需要先握手、单连接还是每调用一条 |

**排序**：先排调用方最常用的接口，再排次要的；不要按后端模块顺序排。

## 4. 单个接口模板（照抄，只替换内容）

~~~markdown
## N.接口中文名

| 项 | 内容 |
|---|---|
| 接口名称 | 中文名（后端名/命令名） |
| 调用方法 | `client.方法名(参数1, 参数2)` 或 `GET /api/v1/xxx` |
| 协议端点 | `cmd = X` / `POST /path` / 事件名 |

### N.1 请求参数

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `参数1` | string | 是 | — | 语义 + 格式 + 不合法时的表现 |
| `参数2` | number | 否 | 0 | 语义；0 代表什么 |

### N.2 返回值

`code`：0 成功；1 xxx；5 xxx；末尾放传输层错误。

| `data` 字段 | 类型 | 说明 |
|---|---|---|
| `字段` | string | 语义；异常/缺省时的取值 |

> 一句话写清最容易误解的语义边界。
~~~

参数或返回里有枚举、数组元素、子结构时，在对应小节后**另起一张表**，表格上方一行引出：

~~~markdown
`items` 元素：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一标识 |
~~~

## 5. 逐项写法约定

| 位置 | 规则 |
|---|---|
| 接口名称 | `中文名（后端名/命令名）`，后端名与代码里的定义一致 |
| 调用方法 | 只写签名或路由，不写实现 |
| 协议端点 | 命令号 / HTTP 方法 + 路径 / 事件名，按项目实际填一个 |
| 参数表 | 5 列固定：参数 / 类型 / 必填 / 默认 / 说明；必填写 `是` `否`，无默认写 `—` |
| 参数说明 | 必须写"不合法或缺省会怎样"，而不是只描述含义 |
| code 摘要 | 一行写完，`code`：0 成功；1 …；5 …；**传输层错误码（服务不可达/超时）固定放最后**——它由客户端本地判定，不是服务端业务码 |
| data 表 | 3 列固定：字段 / 类型 / 说明；字段名带反引号 |
| 注意块 | `>` 引用，1~3 行，只写反直觉的语义（见第 6 节），不重复正文 |
| 交叉引用 | 写"10.查询客户端列表"这种带编号的标题，不写"上面那个接口" |
| 时间 | 必须标时区与格式：本地时间 `YYYY-MM-DD HH:MM:SS`，UTC 写 `2026-11-11T01:45:27Z` 并注明"展示前转本地" |
| 枚举 | 用反引号逐项列全，如 `running` / `stopped` / `updating` |
| 表格内竖线 | 类型写 `object \| null`、`number \| string` 时必须转义 |
| 命名分层 | SDK 转换过的字段用其风格（通常小写驼峰 `pageSize`、`truncated`）；后端原样透传的 JSON 保留原始大小写（`OrderId`、`Total`）。**同文档内不混写，且要能一眼看出哪些是透传** |
| 分页 | 统一字段名（如 `total` / `page` / `pageSize` / `items`），所有接口保持一致，不要一个接口 `list` 一个接口 `items` |
| 认证 | 全局统一的认证放 1.3；个别接口特殊，在"项"表里加一行注明 |

## 6. 每个接口必须回答的 7 个问题

写完一个接口前逐条自问，缺哪条补到"注意"里：

1. **哪些情况算成功但没做事？** 空列表、`found=false`、`current=null`、`delivered=false`、日志空文本——都要明说"不算错误"
2. **哪些情况失败但 `code=0`？** 业务层面的"未命中""未送达"通常不该占用错误码
3. **有没有破坏性副作用？** 删除、覆盖、重启、扣款——写"不可恢复""需二次确认"
4. **失败时 `message` 能否直接展示？** 服务端是回具体原因，还是只有一个码
5. **有没有时效或上限？** 条数上限、超时、缓存时间、数据保留期、单次最大条数
6. **字段是否可能缺失或为 null？** 跨版本兼容场景要写"按空值容错"
7. **是否幂等？重试安全吗？** 尤其写操作，说清重复调用的后果

## 7. 校验清单（交付前逐条过）

- [ ] 方法名、参数顺序、参数名与调用方 SDK **完全一致**
- [ ] `data` 字段与代码真实返回结构**完全一致**，不多不少
- [ ] `code` 摘要覆盖该接口实际可能返回的所有值，没写不存在的
- [ ] 每张表：表头列数 = 分隔行列数 = 数据行列数
- [ ] 编号连续、无跳号，正文交叉引用的编号与标题一致
- [ ] 枚举值、时间格式、路径/分页规则与后端实现一致
- [ ] 没有"可能""大概""应该"这类不确定表述
- [ ] 危险操作都写了二次确认提示
- [ ] 认证/权限要求写清楚了

## 8. 禁止事项

- ❌ 写实现原理、协议字节、帧结构、内部流程
- ❌ 贴大段调用示例或完整页面代码（最多一行签名）
- ❌ 编造代码里不存在的参数、字段、错误码
- ❌ 把内部细节（临时文件、原子替换、缓存策略）写进参数说明，除非影响调用方判断
- ❌ 同一接口写两遍；同一端点不同用法可拆节，但内容不重复
- ❌ 用例式流水账（"先调 A 再调 B"），除非那是必须的组合流程——放"典型流程"单独一节

## 9. 新增一个接口的操作步骤

1. 在调用方 SDK 里找到方法，确认参数顺序与返回结构
2. 在服务端实现里确认：成功/失败分支、字段名、时间格式、上限
3. 需要时实测一次，记下真实响应
4. 用第 4 节模板写入，编号顺延（后续章节与交叉引用编号一并 +1）
5. 按第 7 节清单自检
6. **只改接口文档这一个文件**，不动其他文件

## 10. 常见坑

| 坑 | 正确做法 |
|---|---|
| 照着旧文档或旧 SDK 写 | 动手前先读当前 SDK 与实现，它们可能已被改过 |
| 批量替换编号时误伤标题文字/空格 | 改编号只动数字，不要全局替换整行 |
| 表格少写一列分隔符 | 5 列表头必须跟 5 个 `---` |
| 把"查不到"写成错误 | 查询类通常是 `code=0` + `found=false`；删除/下载不存在才是错误码 |
| 把业务 false 当系统错误 | `delivered=false`、`success=false` 常常是正常结果 |
| 忘记标时间时区 | 服务端混用本地时间与 UTC 时，必须逐字段标注 |
| 分页字段各接口不一致 | 先定统一命名再写，写完回头对一遍 |
| 文档与实现脱节 | 接口变更时把文档同 PR 一起改，否则一个月后没人信它 |

## 11. 硬约束（优先级最高）

以下每条都是可判定的：做不到就是违规，不要"尽量"。

| # | 约束 | 判定为违规的情形 |
|---:|---|---|
| C1 | **只改接口文档这一个文件** | 出现对 `.js`/`.cpp`/`.json`/配置文件的修改；需要改代码时先说明理由并等确认 |
| C2 | **范围受控，一次只做被指定的部分** | 用户说"加一个接口"，却顺手重排其他章节、改措辞、调格式 |
| C3 | **事实必须可追溯** | 写的字段/方法/码值指不出 SDK 或服务端实现的位置 |
| C4 | **拿不到事实就标注，禁止猜** | 编造字段、凭经验补参数、写"应该会返回 xxx" |
| C5 | **文档与实现冲突时以实现为准，并主动报告差异** | 照抄旧文档且未说明；或发现不一致却沉默 |
| C6 | **不写尚未实现的能力** | 出现"预留参数""暂不支持，将来会…""可选扩展" |
| C7 | **格式硬性** | 参数表非 5 列、返回表非 3 列、表头/分隔行/数据行列数不等、编号跳号、`### N.2 返回值` 漏空格 |
| C8 | **每个接口必须有"注意"块** | 只有参数表和返回表，没有 `>` 语义边界说明 |
| C9 | **术语与措辞一致** | 同一概念全文两种叫法（如"客户端"/"设备"混用）；事实描述用"可能/大概/应该/基本上" |
| C10 | **时间与单位必须标全** | 时间无时区、金额无币种、容量/时长无单位、本地时间与 UTC 混用不标注 |
| C11 | **交付前自检，不带病交付** | 校验清单里有未修项仍然交付；发现不一致说"以后再改" |
| C12 | **改已有内容前先确认** | 擅自改写他人在文档里的措辞、结构、示例 |
| C13 | **交付说明只讲变更与待确认** | 回复里复述整篇文档内容、粘贴大段正文、罗列已写过的字段清单 |

**冲突仲裁顺序**：C1~C13 > 第 5 节写法约定 > 第 4 节模板 > 个人偏好。用户的临时指令若与 C1、C4、C7 冲突，先指出冲突再执行。
